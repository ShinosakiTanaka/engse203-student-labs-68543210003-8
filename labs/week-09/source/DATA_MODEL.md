# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

---

## 1. ภาพรวม

**แผนภาพความสัมพันธ์**

```text
users (1) ─────────────────── (N) requests
```

ความสัมพันธ์ระหว่าง `users` และ `requests` เป็นแบบ **One-to-Many (หนึ่งต่อหลาย)** เพราะผู้ใช้ 1 คนสามารถแจ้งคำร้องได้หลายรายการ แต่คำร้อง 1 รายการจะมีผู้แจ้งเพียง 1 คน โดยใช้ `requests.requester_id` เป็น Foreign Key ที่อ้างอิงไปยัง `users.id`

---

## 2. ทำไมต้องแยกเป็น 2 ตาราง

เหตุผลที่ต้องแยก `users` ออกจาก `requests` คือเพื่อ **ลดความซ้ำซ้อนของข้อมูล** และป้องกันปัญหาที่ต้องแก้ข้อมูลเดียวกันในหลายรายการ

เช่น หากเก็บชื่อไว้ในตารางคำร้องทุกอัน ถ้าสมชายแจ้งคำร้องไว้ 50 รายการ แล้ววันหนึ่งเขาขอเปลี่ยนชื่อเป็น "สมคิด ใจงาม" ก็จะต้องตามไปเปลี่ยนข้อมูลถึง 50 ที่ ถ้าแก้ไม่ครบ ข้อมูลจะเกิดความขัดแย้งกัน บางคำร้องเป็นชื่อเก่า บางคำร้องเป็นชื่อใหม่
การแยกเป็น 2 ตารางแล้วใช้ FK ชี้มาหา ID ผู้ใช้ จะทำให้เก็บชื่อไว้ที่เดียว เมื่อเปลี่ยนชื่อที่ตาราง users เพียงครั้งเดียว ข้อมูลในคำร้องทั้งหมดก็จะถูกต้องตามไปด้วยทันที
---

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือก |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY | เป็น ID ตัวเลขที่ใช้ระบุผู้ใช้แต่ละคน ไม่ซ้ำกัน และเหมาะสำหรับใช้เป็น Foreign Key |
| `name` | TEXT | NOT NULL | ใช้เก็บชื่อผู้ใช้ ซึ่งผู้ใช้ทุกคนต้องมีชื่อและไม่สามารถเว้นว่างได้ |
| `department` | TEXT | NOT NULL | ใช้ระบุหน่วยงานหรือแผนกของผู้ใช้ และต้องมีข้อมูล |
| `email` | TEXT | NOT NULL, UNIQUE | ใช้สำหรับติดต่อผู้ใช้ และกำหนด UNIQUE เพื่อป้องกันอีเมลซ้ำกัน |

### ตาราง `requests`

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือก |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | ใช้เป็นรหัสประจำคำร้องแต่ละรายการ ต้องไม่ซ้ำกัน และสามารถใช้รูปแบบที่อ่านง่าย เช่น `REQ-001` |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY | ใช้อ้างอิงผู้แจ้งจากตาราง `users` โดยไม่ต้องเก็บชื่อผู้แจ้งซ้ำในทุกคำร้อง |
| `request_type` | TEXT | NOT NULL, CHECK | ใช้เก็บประเภทคำร้อง และจำกัดค่าให้เป็นประเภทที่ระบบกำหนด |
| `location` | TEXT | NOT NULL | ใช้ระบุสถานที่ที่เกี่ยวข้องกับคำร้อง เช่น ห้องเรียน ห้องปฏิบัติการ หรือสำนักงาน |
| `details` | TEXT | NOT NULL | ใช้เก็บรายละเอียดของปัญหาหรือความต้องการ เพื่อให้ผู้รับผิดชอบเข้าใจคำร้อง |
| `priority` | TEXT       | NOT NULL, DEFAULT `'normal'`, CHECK   | ใช้ระบุระดับความเร่งด่วน โดยกำหนดค่าเริ่มต้นเป็น `normal` และอนุญาตเฉพาะ `normal` หรือ `urgent`        |
| `status` | TEXT | NOT NULL, DEFAULT `'pending'`, CHECK  | ใช้ติดตามสถานะของคำร้อง โดยเริ่มต้นเป็น `pending` และอนุญาตเฉพาะ `pending`, `in-progress`, `completed` |
| `created_at` | TEXT | NOT NULL, DEFAULT `CURRENT_TIMESTAMP` | ใช้บันทึกวันและเวลาที่สร้างคำร้องโดยอัตโนมัติ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

### ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน

`users.id` ใช้ `INTEGER` เพราะเป็นหมายเลขประจำตัวผู้ใช้ เช่น `1`, `2`, `3` ซึ่งเหมาะสำหรับใช้เป็น ID และ Foreign Key ในการเชื่อมโยงกับตาราง `requests`

ส่วน `requests.id` ใช้ `TEXT` เพราะรหัสคำร้องอาจต้องการรูปแบบที่อ่านและจดจำได้ง่าย เช่น `REQ-001`, `REQ-002` ทำให้สามารถแยกแยะรหัสคำร้องได้สะดวก

### ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว

`CHECK constraint` ทำหน้าที่เป็นกฎบังคับในระดับ Database เพื่อป้องกันข้อมูลที่ไม่ถูกต้อง แม้ว่าข้อมูลจะถูกเพิ่มหรือแก้ไขผ่านช่องทางอื่นที่ไม่ได้ผ่าน API

ตัวอย่างเช่น `status` กำหนดให้รับเฉพาะ `pending`, `in-progress` และ `completed` หากมีการพยายามบันทึกค่าอื่น Database จะปฏิเสธข้อมูลนั้น

## 5. ตัวอย่างการใช้ JOIN

ใช้ `JOIN` เพื่อเชื่อมข้อมูลผู้แจ้งจากตาราง `users` เข้ากับข้อมูลคำร้องในตาราง `requests`

```sql
SELECT r.id, u.name, r.details
FROM requests r
JOIN users u ON u.id = r.requester_id
WHERE u.department = 'วิศวกรรมซอฟต์แวร์'
ORDER BY r.id;
```

**ผลลัพธ์ที่ได้**

| id | name | details |
|---|---|---|
| REQ-001 | สมชาย ใจดี | เครื่องปรับอากาศไม่ทํางานตั้งแต่เช้า |
| REQ-002 | สุภาวดี รักเรียน | เข้าสู่ระบบห้องปฏิบัติการไม่ได้ |
| REQ-004 | สมชาย ใจดี | คอมพิวเตอร์เครื่องที่ 5 เปิดไม่ติด |
| REQ-006 | สุภาวดี รักเรียน | เครื่องพิมพ์ใช้งานไม่ได้ |

จากผลลัพธ์จะเห็นว่า `requests` เก็บเพียง `requester_id` แต่สามารถใช้ `JOIN` เพื่อดึงชื่อผู้ใช้จาก `users` มาแสดงร่วมกับข้อมูลคำร้องได้

---

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

จากการทดสอบ JOIN ทำให้สามารถรวมข้อมูลจากตาราง users และ requests ได้
ใน Database เราเก็บ requester_id ไว้ในคำร้อง แต่สามารถดึงชื่อผู้แจ้งจาก users มาแสดงได้
ผลลัพธ์ที่ได้สามารถนำไปใช้เป็นข้อมูลที่ API ส่งต่อให้ React ได้
ทำให้ข้อมูลใน Database ไม่ซ้ำ และฝั่ง React ก็ได้ข้อมูลที่พร้อมนำไปแสดง
